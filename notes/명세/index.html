Dantok Stateful Event-Driven Actor Runtime

2026년 8월 21일

Dantok Stateful Event-Driven Actor Runtime

  1. Purpose

Dantok의 실행 모델을 중앙 scheduler가 캐릭터의 발화를 순차적으로 지시하는 구조에서,

«지속 상태를 가진 여러 Actor가 공유 세계를 관찰하고, 각자의 상태에 따라 독립적으로 인지·평가·행동하며, 그 결과를 하나의 authoritative Room state에 반영하는 구조»

로 확장한다.

핵심 원칙은 다음과 같다.

  • Stateful — Room과 Actor의 상태는 사건 사이에도 지속된다.
  • Event-driven — 지속적인 polling/tick을 필수로 하지 않고 사건과 의미 있는 시간 경계가 계산을 촉발한다.
  • Actor-oriented — 각 Character가 독립적인 cognitive lifecycle을 가진다.
  • Authoritative world — Agency는 Actor에 분산되지만 shared-world authority는 Room에 있다.
  • Recoverable reality — 확정된 세계 상태는 transient execution의 생존 여부와 무관하게 복구 가능해야 한다.

현재 Dantok 구현은 한 Node process 안에서 deterministic scheduling, generation slot, interpretation/realization, settlement, publication, commit 및 global logical-attempt gate를 중앙 Room Runtime이 조합한다. 현재 scheduling state에는 character별 pressure, threshold, cooldown, channel attention 및 read cursor가 이미 존재한다. Target architecture는 이 기존 모델을 단순히 "async/await"로 병렬화하는 것이 아니라 행동 agency의 소유권을 Room에서 Character-Actor로 재배치한다.

  1. Core Model

                      ROOM / WORLD
                       │
          authoritative state
                       │
      ┌────────────────┼────────────────┐
      │                │                │
      ▼                ▼                ▼
 Marilyn Actor     Audrey Actor      Grace Actor
      │                │                │
 perception        perception       perception
      ↓                ↓                ↓
  appraisal         appraisal        appraisal
      ↓                ↓                ↓
   pressure         pressure         pressure
      ↓                ↓                ↓
  realization      realization      realization
      │                │                │
      └────────────────┼────────────────┘
                       ↓
                action requests
                       ↓
             authoritative commit
                       ↓
                  ROOM STATE'

핵심 관계는 다음과 같다.

«Actor가 행동을 생성하고, Room이 그 행동이 공유 세계의 사실이 되는 것을 확정한다.»

이는 다음 두 문장을 함께 만족한다.

«Agency is distributed. World authority is centralized.»

  1. Architectural Boundaries

3.1 Room

Room은 shared-world authority다.

Room owns

  • authoritative Room state
  • canonical event history
  • message publication
  • commit
  • shared-world conflict resolution
  • room-wide invariants
  • actor가 관찰할 world snapshot/version
  • durable persistence boundary
  • shared temporal context

Room does not directly own

  • 특정 Actor에게 발화를 명령하는 것
  • Actor의 appraisal
  • Actor의 pressure
  • Actor의 내부 cognitive state

현재 구현에서는 이러한 책임들이 deterministic scheduler와 generation lifecycle에 집중되어 있다. Target에서는 world authority와 commit은 Room에 남기고 행동의 발의권을 Actor로 이동시킨다.

3.2 Actor

Actor는 특정 Room 안에서 Character를 실행하는 autonomous cognitive unit이다.

Actor가 소유할 수 있는 상태:

  • personality / Character configuration
  • appraisal state
  • pressure
  • attention
  • read/unread state
  • actor-local memory
  • in-flight cognitive work
  • pending action proposal
  • 기타 Character-specific persistent state

Actor는 다른 Actor의 내부 상태나 authoritative Room state를 직접 mutation하지 않는다.

Actor A ──action request──→ Room Actor B ──action request──→ Room

  1. Character and Actor

Character와 Actor는 개념적으로 구별한다.

  • Character — 인물의 정의, 정체성 및 정적 구성
  • Actor — 특정 Room에서 그 Character가 실제로 살아 움직이는 실행 인스턴스

Character + Room-specific state ↓ Actor instance

따라서 같은 Character를 여러 Room에서 사용할 수 있다.

Marilyn Character │ ┌───┴────┐ ▼ ▼ Actor@A Actor@B

Personality/configuration은 공유할 수 있지만 pressure, relationship, read state, appraisal, memory 등 Room-specific state는 독립적일 수 있다.

  1. Cognitive Pipeline

기본 cognitive lifecycle은 다음과 같다.

WORLD EVENT ↓ PERCEPTION ↓ APPRAISAL ↓ PRESSURE / INTERNAL STATE UPDATE ↓ ACTION ELIGIBILITY ↓ REALIZATION ↓ ACTION / PUBLISH REQUEST

이 단계는 semantic model이다.

각 단계가 몇 개의 LLM invocation으로 구현되는지는 별도의 execution decision이다.

가능한 구현:

  • 단일 LLM 호출
  • 복수 LLM 호출
  • 직렬 호출
  • 병렬 호출
  • 부분 병렬
  • deterministic computation + LLM 조합

따라서:

«Cognitive decomposition과 invocation topology를 conflation하지 않는다.»

  1. Interpretation Asymmetry

Interpretation에는 최소 두 가지 의미적 책임이 있을 수 있다.

6.1 Common Ground / Knowledge Interpretation

공유 세계가 무엇을 알게 되었는지를 해석한다.

event / message ↓ CG / knowledge interpretation ↓ shared knowledge update

6.2 Actor Appraisal Interpretation

각 Actor가 사건을 어떻게 평가하는지를 해석한다.

shared event / context ↓ ┌─────┼─────┐ M A G ... ↓ ↓ ↓ appraisal

같은 사건도 Actor별로 다른 appraisal을 가질 수 있다.

6.3 Logical Dependency vs Invocation Ordering

CG 결과가 appraisal의 논리적 입력일 수 있다.

CG → appraisal

그러나 이는 반드시:

LLM Call #1 → LLM Call #2

를 의미하지 않는다.

가능한 execution strategy는 열어 둔다.

  • strict serialization
  • overlapping computation
  • speculative appraisal + re-evaluation
  • joint single-call output
  • shared interpretation + parallel actor appraisal

의미론적 dependency와 물리적 execution ordering은 별개의 축이다.

  1. Trigger Asymmetry

Interpretation과 realization은 동일한 trigger model을 갖지 않는다.

7.1 Interpretation

공통 Room event가 trigger가 될 수 있다.

NEW ROOM EVENT ↓ shared interpretation

7.2 Actor Appraisal

Actor-specific perception 또는 Actor-specific read event가 trigger가 될 수 있다.

Actor observes / reads event ↓ Actor appraisal

7.3 Realization

Actor-local condition이 trigger가 된다.

pressure >= threshold ↓ realization

따라서:

«해석은 공통 트리거일 수 있고, 실현은 분산 트리거다.»

이 비대칭성은 architecture의 의미론이며, invocation topology와 동일시하지 않는다.

  1. Read / Unread

메시지는 Actor별 read state를 가질 수 있다.

Message #42

Marilyn unread Audrey read Grace read Elizabeth unread

따라서:

«message exists ≠ actor has perceived message»

를 구별할 수 있다.

message published ↓ actor-specific unread state ↓ actor reads ↓ actor appraisal

"read"는 appraisal의 중요한 distributed trigger가 될 수 있지만 유일한 trigger일 필요는 없다.

  1. Event Granularity vs Computation Granularity

하나의 semantic event가 하나의 LLM invocation을 강제하지 않는다.

예:

Message 41 → read Message 42 → read Message 43 → read

가 반드시:

Appraisal(41) Appraisal(42) Appraisal(43)

이어야 하는 것은 아니다.

다음과 같은 구현도 가능하다.

read 41 read 42 read 43 ↓ batched appraisal

따라서 다음을 독립적으로 결정한다.

  • event emission granularity
  • state transition granularity
  • cognitive invocation granularity
  • LLM batching/debouncing/coalescing

Batching은 semantic contract가 아니라 execution strategy다.

  1. Pressure

Pressure는 Actor-local dynamic state다.

현재 구현에서도 캐릭터별 pressure, threshold, cooldown 등의 상태가 존재하며 scheduler가 이를 이용해 "ScheduledTurn"을 계산한다.

Target에서는 pressure의 ownership을 Actor 쪽으로 명확히 이동한다.

ActorState ├─ pressure └─ lastPressureUpdate

10.1 Lazy Temporal Advancement

시간에 따른 pressure 변화가 함수로 표현 가능하다면:

pressure(t1)

pressure(t0) + accumulation(t0 → t1)

처럼 현재 시점에서 advance할 수 있다.

따라서 continuous tick을 요구하지 않는다.

10.2 Scheduled Semantic Boundary

threshold crossing이 의미 있는 사건이라면:

current state ↓ next meaningful boundary ↓ scheduled activation

으로 처리할 수 있다.

따라서:

«dynamic state simulation과 continuous polling은 별개의 문제다.»

  1. Event-Driven Runtime

Runtime은 continuous tick을 필수로 하지 않는다.

예시 event:

  • "MessagePublished"
  • "MessageRead"
  • "RelationshipChanged"
  • "AttentionChanged"
  • "PressureThresholdReached"
  • "CooldownExpired"
  • "TemporalBoundaryReached"
  • "ActorActionCommitted"

Event는 해당 Actor 또는 Room의 state transition과 cognitive work를 trigger할 수 있다.

  1. Asynchronous Actor Execution

각 Actor의 cognitive pipeline은 다른 Actor의 external latency 때문에 전체적으로 직렬화되지 않는다.

Marilyn ───── realization ──────────────→

Audrey ── appraisal ───── realization ─→

Grace ────── realization ─────────────→

                     ↓
                Room boundary

목표는:

«LLM latency를 room-level latency가 아니라 actor-level latency로 국소화하는 것»

이다.

다만 Actor pipeline 내부에서 어느 stage를 overlap할지 여부는 별도의 execution policy다.

  1. Realization as Action Proposal

Realization은 shared world의 즉각적인 사실이 아니다.

Actor state / world snapshot ↓ realization ↓ action proposal

Realization 중 Room world가 변하는 것은 정상적이다.

따라서:

«Realization completion ≠ publication»

이다.

  1. Stale Realization

예:

t0 A reads S0 A starts realization

    ├── B commits event
    ├── C changes shared state
    └── Room becomes S3

t1 A realization completes

A의 결과는 자동으로 폐기되거나 자동으로 채택되지 않는다.

완료 후 현재 world와의 관계를 판단한다.

accept revalidate abandon retry / re-realize cancel

중 하나가 될 수 있다.

  1. Stale Detection vs Impact Assessment

두 문제를 구분한다.

Stale detection

«내가 본 world가 현재와 달라졌는가?»

예:

sourceVersion = 41 currentVersion = 42

이는 비교적 저비용으로 판단할 수 있다.

Impact assessment

«그 변화가 내 realization을 실제로 무효화하는가?»

예:

E42 = unrelated small talk

는 stale이지만 반드시 invalid하지 않다.

반면:

E42 = "나 지금 집에 가야 해"

가 해당 realization의 전제와 직접 관련된다면 invalid할 수 있다.

따라서:

«stale ≠ invalid»

이다.

  1. Impact Assessment Cost

Impact assessment 자체가 realization보다 무거운 정상 경로가 되어서는 안 된다.

따라서 기본 경로는 가능한 한 inexpensive하게 유지한다.

가능한 방법:

  • version comparison
  • causal dependency metadata
  • action-specific invalidation rule
  • event type / relevance metadata
  • lightweight semantic predicate

필요할 때만 보다 비싼 semantic assessment를 사용한다.

그러나 특정 "O(1)" rule이나 특정 evaluator를 이 명세에서 강제하지 않는다.

  1. Cancellation

Staleness가 발생했다고 해서 반드시 진행 중 LLM computation을 취소하는 것은 아니다.

world change ↓ impact assessment ↓ low impact → continue high impact → cancel / re-plan

Cancellation은 최적화 policy다.

가능한 mechanism:

  • "AbortSignal"
  • provider-native cancellation
  • runtime-level cancellation
  • no cancellation + completion-time validation

따라서:

«Stale handling은 필수지만 early cancellation은 선택적이다.»

Cancellation policy 자체는 열린 축이다.

  1. Causal Lineage

Room의 canonical history는 단순한 total ordering 이상의 정보를 필요로 할 수 있다.

E41 ↓ A observed E41 ↓ A realization R1 ↓ B commits E42 ↓ A commits E43

단순한 chronological order는:

E41 < E42 < E43

이지만 이것은 E43이 E42를 인지했다는 뜻이 아니다.

따라서:

«Canonical ordering과 causal awareness를 동일시하지 않는다.»

  1. Action Provenance

Action proposal은 가능한 범위에서 다음 provenance를 가질 수 있다.

ActionProposal ├─ actor ├─ sourceWorldVersion ├─ observedEvents ├─ causal dependencies └─ generated action

이를 통해:

«이 행동은 어떤 세계를 보고 생성되었는가?»

를 복원할 수 있다.

  1. No Retroactive Causality

다음 상황은 허용된다.

E1 published A observes E1 A starts realization

E2 published

A commits action derived from E1

A가 E2를 인지하지 않았다는 사실은 유지되어야 한다.

따라서:

«Later commit order alone must not imply earlier cognitive awareness.»

이를 history representation과 downstream interpretation이 보존해야 한다.

"In-Reply-To"는 하나의 구현 수단일 수 있지만 architectural invariant 자체는 아니다.

  1. Concurrent State Transitions

동시성을 전면적으로 금지하지 않는다.

21.1 Independent mutations

A → message A B → message B

둘 다 authoritative history에 들어갈 수 있다.

21.2 Conflicting mutations

S0 ├─ A: relationship = 0.7 └─ B: relationship = 0.4

동일한 shared variable에 incompatible mutation이 들어오면 resolution이 필요하다.

핵심 원칙:

«독립적인 state transition은 concurrent할 수 있다. Conflicting transition은 하나의 일관된 결과로 resolve되어야 한다.»

  1. Conflict Semantics

가능한 전략:

  • serialization
  • optimistic concurrency + retry
  • merge
  • semantic delta
  • domain-specific resolution

그러나 특정 전략을 선결하지 않는다.

특히:

«CRDT를 기본 모델로 채택하지 않는다.»

Semantic delta는 mutation representation으로 유용할 수 있지만, 모든 Dantok state transition이 commutative하다고 가정하지 않는다.

Relationship이나 Common Ground와 같이 순서와 causal context가 의미의 일부인 state가 있을 수 있다.

  1. Event Fan-out

Actor autonomy는 하나의 Room event가 여러 Actor에게 관찰될 수 있음을 뜻한다.

Room Event │ ├── Actor A ├── Actor B ├── Actor C └── Actor D

그러나:

«Event fan-out ≠ cognitive fan-out»

이다.

모든 Actor가 모든 event에 대해 expensive appraisal을 수행할 필요는 없다.

  1. Activation Gate

Appraisal 이전에 inexpensive eligibility filtering을 둘 수 있다.

Room Event ↓ Actor eligibility ↓ ┌────┴────┐ skip activate ↓ appraisal

가능한 filter:

  • visibility
  • read state
  • attention
  • event type
  • actor participation
  • cooldown
  • relevance metadata

Gate가 반드시 Room에 위치해야 하는 것은 아니다.

가능한 위치:

Room Actor shared event router

중 하나다.

  1. Fan-out and Deployment

Actor fan-out은 domain semantics이고, serverless activation fan-out은 execution/deployment semantics다.

Resident runtime:

1 event → N in-memory notifications

Stateful serverless:

1 event → N activations

따라서 serverless에서 activation 비용이 커진다고 해서 Actor architecture 자체를 centralized scheduler로 되돌릴 이유는 없다.

Deployment layer에서는 다음을 선택할 수 있다.

  • event filtering
  • batching
  • co-location
  • lazy activation
  • shared preprocessing
  • activation throttling
  1. Common Ground Dependency

CG와 Appraisal 사이의 semantic dependency가 강한 경우에는 strict ordering이 필요할 수 있다.

예:

E42 ↓ CG interpretation ↓ "X is known to be guilty" ↓ Actor appraisal

이를 위해 다음 execution modes를 허용한다.

Strict

E ↓ CG ↓ Appraisal

Speculative

   ┌→ CG ───────┐

E ─────┤ ↓ └→ appraisal → reconcile

Joint

E ↓ single cognitive invocation ↓ CG + appraisal

어떤 방식을 택할지는 execution policy다.

  1. Speculative Cognition

Speculative appraisal을 사용하는 경우 speculative result는 authoritative state가 아니다.

speculative appraisal ↓ CG result available ↓ validate ↓ accept / discard / recompute

따라서:

«Speculative cognition never directly establishes authoritative world state.»

  1. Shared World vs Actor State

Room state

공유 현실이다.

messages canonical event history shared knowledge room-wide relationships world facts

Actor state

특정 Actor가 가진 관점과 내부 상태다.

pressure attention read/unread appraisal memory intent in-flight cognition

핵심 원칙:

«Actor state는 agency를 나타내고, Room state는 shared reality를 나타낸다.»

  1. Event History

Room은 canonical event history를 가진다.

Actor는 그 history를 독립적인 perception timing으로 처리할 수 있다.

Room history: E1 → E2 → E3 → E4

Marilyn: E1 → E2 → E4

Audrey: E1 → E2 → E3 → E4

따라서 Room의 canonical ordering과 Actor의 perception timing은 동일한 개념이 아니다.

  1. Time and Simulation

시간은 세 가지 방식으로 사용한다.

Event time

message published ↓ actor reacts

Elapsed time

pressure(t) attention(t) relationship decay(t)

Scheduled semantic boundary

threshold crossing cooldown expiry attention deadline

세 방식 모두 continuous computation을 요구하지 않는다.

  1. Latency Semantics

비동기 구조에서 provider latency는 개별 Actor의 behavior process에 속한다.

A starts realization ─────────────→ 12s B starts realization ───→ 4s

그러나:

«completion order ≠ social importance ≠ authoritative event order»

이다.

빠른 Actor가 반드시 사회적으로 우선하는 것도 아니고, 느린 Actor가 반드시 행동 기회를 잃는 것도 아니다.

  1. Latency Fairness

Provider latency가 social dynamics를 왜곡하는지는 관측 대상이다.

가능한 향후 policy:

  • pressure adjustment
  • cooldown
  • simulated response delay
  • priority policy
  • starvation prevention

그러나 현재 specification은 이를 강제하지 않는다.

«Latency fairness는 검증 대상이지, 선결된 보정 규칙이 아니다.»

  1. Dynamic Simulation vs Tick

동적 state를 유지하기 위해 반드시 resident tick loop를 사용할 필요는 없다.

가능한 구성:

persistent state + last-updated timestamp + state transition function + meaningful activation

따라서 stateful serverless에서도 dynamic cognitive simulation이 가능하다.

다만 매우 높은 주파수의 물리/수치 simulation과 같이 매 순간 계산이 의미 자체인 workload라면 resident/tick execution이 더 적합할 수 있다.

  1. Persistence Model

Room state와 Actor state는 논리적으로 구별하지만 반드시 별도의 physical datastore를 사용해야 하는 것은 아니다.

가능한 구조:

single durable store ├─ Room state └─ Actor state

또는:

Room store Actor store

즉 "dual persistence"는 architectural requirement가 아니라 implementation topology다.

  1. Actor State Recovery

핵심 invariant:

«Actor state는 필요한 범위에서 canonical Room history와 Character configuration으로 복구 가능해야 한다.»

Room history ↓ Actor reconstruction ↓ derived Actor state

이는 모든 Actor state를 완전한 event-sourced projection으로 구현해야 한다는 뜻은 아니다.

중요한 것은:

«Room history가 Actor transient state보다 높은 authority를 가진다.»

  1. Durable Semantic State vs Execution State

Actor state는 두 종류로 구분할 수 있다.

Durable semantic state

잃어버리면 안 되는 상태.

예:

  • read cursor
  • durable memory
  • actor-owned relationship state
  • persistent configuration

Reconstructible execution state

잃어버려도 복구 가능한 상태.

예:

  • in-flight realization
  • temporary appraisal
  • activation marker
  • transient cache

따라서 crash 후:

Room committed E42 Actor crashed ↓ recover ↓ reconstruct Actor state ↓ resume / discard stale work

가 가능해야 한다.

  1. Commit / Actor State Ordering

Room commit은 Actor의 별도 post-commit persistence 성공에 의존해서는 안 된다.

권장 logical flow:

Actor proposal ↓ Room commit ↓ canonical event ↓ Actor observes own committed event ↓ Actor state projection advances

Actor persistence가 실패하면 committed event가 취소되는 것이 아니라 Actor projection이 뒤처진 것으로 취급한다.

이후 recovery:

canonical history ↓ missing projection ↓ rebuild

한다.

따라서 2PC를 요구하지 않는다.

  1. Duplicate Action Prevention

비동기 runtime에서 다음 failure를 고려한다.

proposal submitted Room commits Actor crashes before recording completion Actor restarts Actor submits same proposal again

따라서 action proposal은 idempotency identity를 가질 수 있다.

ActionProposal ├─ actorId ├─ proposalId └─ sourceWorldVersion

Room은 이미 처리된 logical proposal의 중복 commit을 방지해야 한다.

  1. Self-Healing

핵심 recovery invariant:

«재기동 후 Actor state는 canonical Room history와 eventual consistency를 이뤄야 한다.»

동일한:

  • Room history
  • Character configuration
  • deterministic state transition rules

가 주어지면 필요한 Actor state를 재구성할 수 있어야 한다.

LLM의 비결정적인 결과는 무조건 replay하는 대상이 아니다. 필요한 경우 결과 또는 그 결과가 생성한 committed event를 persistence boundary에 보존한다.

  1. Failure Model

다음 failure는 정상적으로 발생할 수 있는 것으로 취급한다.

  • LLM timeout
  • provider failure
  • Actor process termination
  • serverless activation termination
  • duplicate delivery
  • delayed event
  • stale realization
  • lost transient cognition
  • persistence failure
  • retry

따라서:

«실행 중인 computation의 생존을 세계 상태의 유일한 근거로 삼지 않는다.»

Canonical world state는 committed state/event로 정의한다.

  1. Runtime Lifecycle

41.1 Resident Runtime

Actor execution context가 계속 존재할 수 있다.

Room ├─ Actor A — idle ├─ Actor B — working ├─ Actor C — idle └─ Actor D — idle

이벤트가 오면 resident Actor가 wake/resume한다.

여기서 "wake"는 이미 존재하는 execution context의 재개를 의미한다.

41.2 Stateful Serverless Runtime

Logical state는 지속하지만 execution context는 필요에 따라 activation될 수 있다.

durable Room / Actor state ↓ event ↓ actor activation ↓ state load / reconstruction ↓ cognitive work ↓ commit ↓ execution suspends / ends

여기서는 "activation"을 주 용어로 사용한다.

  1. Stateful Serverless

Stateful serverless는 architecture의 정의가 아니라 deployment/execution model이다.

핵심 특성은:

«persistent logical state without persistent compute»

이다.

따라서:

logical Room / Actor ↓ durable state ↓ event ↓ compute activation ↓ state transition

이 가능하다면 Dantok의 Actor architecture를 stateful serverless 위에 구현할 수 있다.

Resident runtime과 비교할 때 판단 기준:

  • execution lifetime
  • async work semantics
  • timer / scheduled activation
  • state durability
  • concurrency guarantees
  • activation cost
  • operational constraints

이다.

  1. Runtime Portability

Core runtime semantics는 특정 cloud provider에 종속되지 않는다.

  1. Core Invariants

I1. World Authority

Room만 authoritative shared-world state를 확정한다.

I2. Actor Autonomy

Actor는 자신의 cognitive state와 행동 여부를 독립적으로 결정한다.

I3. No Direct Actor Mutation

Actor는 다른 Actor의 내부 상태나 authoritative Room state를 직접 mutation하지 않는다.

I4. Concurrent Cognition

Actor cognitive pipelines는 서로의 external latency 때문에 전역적으로 직렬화되지 않는다.

I5. Commit Consistency

Concurrent action requests는 하나의 일관된 authoritative world history로 수렴한다.

I6. Temporal Continuity

Actor state는 execution inactivity와 무관하게 시간 모델상 연속성을 가진다.

I7. Lazy Temporal Computation

시간의 경과를 표현하기 위해 매 순간 computation을 수행할 필요는 없다.

I8. Stale Realization Safety

Realization은 시작 당시 world state를 바탕으로 만들어진 action proposal이며 완료 시점 world와의 관계를 재평가할 수 있어야 한다.

I9. Invocation Independence

Semantic cognitive stages와 LLM invocation topology는 별개의 설계축이다.

I10. Trigger Independence

Shared interpretation, Actor appraisal, pressure update 및 realization은 동일한 trigger model을 공유할 필요가 없다.

I11. Event / Computation Separation

Event의 semantic granularity와 실제 computation invocation granularity는 동일할 필요가 없다.

I12. Agency / Authority Separation

Agency는 Actor에 분산되고 authority는 Room에 집중된다.

I13. Conflict Specificity

Conflict resolution은 state semantics에 따라 결정하며 모든 state transition이 commutative하다고 가정하지 않는다.

I14. Latency Locality

External provider latency가 불필요하게 Room 전체의 cognitive progress를 block하지 않아야 한다.

I15. Causal Provenance

Action은 가능한 범위에서 자신이 관찰한 world state와 causal dependency를 식별할 수 있어야 한다.

I16. No Retroactive Causality

Commit order만으로 Actor가 이후 event를 인지했다고 추론하지 않는다.

I17. Speculative Non-Authority

Speculative cognition은 authoritative state transition을 직접 확정하지 않는다.

I18. Recoverability

Actor state는 canonical Room history와 Character configuration을 통해 필요한 범위에서 복구 가능해야 한다.

I19. Idempotent Commit

동일한 logical action의 retry가 중복 world transition을 생성하지 않아야 한다.

I20. Projection Independence

Room commit은 Actor post-commit persistence의 성공 여부와 독립적이어야 한다.

I21. Fan-out Containment

모든 Room event가 모든 Actor의 expensive cognitive computation을 요구해서는 안 된다.

I22. Assessment Boundedness

Stale handling을 위한 meta-assessment가 정상 realization보다 더 큰 computational burden이 되는 구조를 기본 경로로 삼지 않는다.

  1. Architectural Tensions to Measure

Open axis는 무관심한 미결 상태가 아니라 검증해야 할 질문이다.

T1. Stale Cost

비동기 realization이 얼마나 자주 stale되는가?

T2. Causal Quality

Chronological ordering만으로 actor behavior의 causal coherence가 충분한가?

T3. Fan-out Cost

Event 하나당 실제 appraisal invocation이 몇 개 발생하는가?

T4. CG Dependency

CG 결과를 기다리지 않고 실행한 speculative appraisal이 얼마나 자주 invalidated되는가?

T5. Recovery Cost

Actor projection을 history에서 재구성하는 비용은 어느 정도인가?

T6. Latency Fairness

Provider latency가 실제 발화 분포를 왜곡하는가?

이 질문들은 architecture를 바꾸기 전에 관측하고 측정할 대상이다.

  1. Design Principles

이 architecture의 핵심 설계 원칙은 다음과 같다.

48.1 Separate semantics from execution

«의미론적 stage와 실제 invocation을 분리한다.»

48.2 Separate agency from authority

«Actor가 행동을 제안하고 Room이 세계를 확정한다.»

48.3 Separate chronology from causality

«event order와 actor awareness를 동일시하지 않는다.»

48.4 Separate event fan-out from computation fan-out

«하나의 event가 여러 Actor에게 보인다고 해서 반드시 여러 expensive computation이 필요하지는 않다.»

48.5 Separate stale detection from invalidation

«version mismatch가 곧 semantic invalidity는 아니다.»

48.6 Separate logical persistence from execution residency

«logical Actor/Room이 지속된다고 해서 process가 반드시 상주해야 하는 것은 아니다.»

48.7 Separate failure recovery from transaction coupling

«Actor persistence와 Room commit을 하나의 distributed transaction으로 묶지 않고 canonical Room state에서 projection을 복구할 수 있다.»

48.8 Do not conflate open axes

«한 축의 선택이 다른 축의 선택을 자동으로 결정한다고 가정하지 않는다.»

  1. Target Runtime Definition

«Dantok Runtime은 지속적인 Room과 Character-Actor state를 보유하고, 사건과 의미 있는 시간 경계를 통해 개별 Actor의 인지 pipeline을 독립적으로 활성화하며, 그 결과를 하나의 authoritative Room history로 수렴시키는 stateful, event-driven, actor-oriented runtime이다.»

보다 압축하면:

«Distributed agency, centralized world authority, concurrent cognition, explicit causality, recoverable reality.»

한국어로:

«행동의 agency는 분산하고, 세계의 권위는 중앙화하며, 인지는 병렬화할 수 있지만, 인과관계는 보존하고, 확정된 현실은 항상 복구 가능하게 한다.»

  1. Relationship to Current Architecture

현재 구현은 잘못된 구현으로 규정하지 않는다.

현재 구조는:

Room ↓ pressure / scheduling ↓ speaker selection ↓ generation ↓ settlement ↓ commit ↓ next turn

이라는 structure-centered approximation으로서 일관성을 가진다.

Target은 이를:

Room / World │ ├── Actor A ├── Actor B ├── Actor C └── Actor D │ independent cognition │ action proposals │ ▼ authoritative Room

이라는 agency-centered approximation으로 확장한다.

따라서 Target adoption은 단순한 performance refactor가 아니라 Dantok이 Character agency를 어느 수준까지 simulation semantics로 채택할 것인가에 대한 architectural decision이다.

  1. Final Architectural Principle

«The Room is the world, not the puppeteer. The Actor is the agent, not the world. Cognition may proceed concurrently. Reality is established authoritatively. Causality is preserved explicitly. Execution may disappear; state may not.»
